# SG2002 硬件编码运动向量：板端验证

**已验证 H.265 硬件编码后，可以直接从驱动私有 `mvCol` 缓冲区读出并解析运动向量。
板端不依赖 FFmpeg，也不进行软件解码。**

本次只验证向量获取，没有接入实时相机、LK 或 VIO。

## 实测路径

```text
已知运动的 YUV420p 测试图，640×400
    ↓ CVI_VENC_SendFrame
SG2002 H.265 硬件编码，Normal-P、GOP 60、固定 QP 20
    ↓ CVI_VENC_GetStream 完成
查 ION 分配表 → VENC_0_H265_mvCol
    ↓ /dev/mem 只读映射该保留内存
A53 解析打包字段 → 导出带网格位置的 vectors.csv
```

公开的 `VENC_STREAM_S` 不返回逐块向量，本实验通过链接器 `--wrap` 给 SDK sample
增加诊断代码，在每帧编码完成后读取缓冲区。文件输入模式逐帧 Send/Get，下一帧不会
在当前快照期间提交。没有为获取向量重编译或替换内核模块。

旧版预编译 `sample_venc` 的 sample 对象与当前 `PIC_CUSTOMIZE` 枚举不一致，
首次 640×400 测试在创建编码通道前失败。已将全部 sample 对象按当前头文件重新编译至
独立安装目录，再执行下面的成功测试。
诊断 wrapper 屏蔽旧 libsys 内部 `system("devmem ...")` 的全局功耗寄存器改写。

## 验证结果

六组最终测试共 **76 个编码帧、70 个 P 帧向量导出**。
H.264 和 H.265 的另一次各 16 帧试编码也均成功，回传电脑检查码流均为 640×400、16 帧。
H.264 本次没有发现同名的可读取向量缓冲区；这不证明 H.264 硬件无法导出向量。

| 图像的实际逐帧运动 dx,dy（px） | 缓冲区解析值 x,y | 转换后的向前位移（px） |
|---|---|---|
| 静止 | 0, 0 | 0, 0 |
| +8, +4 | −32, −16 | +8, +4 |
| −6, +2 | +24, −8 | −6, +2 |
| +1.5, +0.75 | −6, −3 | +1.5, +0.75 |

数值符合“当前位置指向参考帧、单位为 1/4 像素”，用于向前预测时需要取负并除以 4。
以上为有效内部网格点的中位数，不意味着每个编码向量都精确等于真实运动。

额外做了两项核对：

- **逐帧改变方向**：8 个运动 P 帧依次包含不同位移及静止，所有帧解析出的内部点中位数
  与对应帧的预期位移完全一致，排除了本测试中读错交替缓冲区而延迟一帧的问题。
- **四象限分别运动**：四区域分别移动 `(8,4)`、`(-6,2)`、`(3,-5)`、`(-4,-3)`，
  对应网格的方向和位置正确。排除外缘及区域边界 32 px 后，所有 P 帧的有效内部点中
  约 **99.89%** 与预期位移完全一致。该值包含开头的静止 P 帧，不是自然图像的跟踪准确率。

板端导出的每个 P 帧包含 **40×25＝1000 个 16×16 网格位置**，其中部分为帧内编码或
无有效向量，`inter_flag=0` 的记录不能作为初值。此网格是硬件的 collocated MV 表，
不是全部编码 PU 分区的完整运动信息。

## 已解析的实验格式

下面是针对本板、当前固件、该编码配置，通过已知运动测试推导和验证的格式，
**不是厂商公开的稳定 ABI**。

- 实测 ION 名为 `VENC_0_H265_mvCol`，本轮物理地址 `0x8ba3d000`，分配长度 **24576 B**。
  地址从 ION 列表发现，未把此地址当作永久地址；只允许映射本板的保留内存范围。
- SDK 为每个重建槽保留的步长是
  `ceil(width/64) * ceil(height/64) * 128`，640×400 时为 **8960 B**。
- 当前 Normal-P 配置实际使用两个重建槽。本测试观察并以逐帧变向序列验证了
  `slot = stream.u32Seq % 2`。**正式接口必须使用驱动的 `EncOutputInfo.reconFrameIndex`，
  不应依赖序号取模**。
- 在每个槽的起始区域，按 64×64 CTU 光栅顺序排列；每 CTU 有四行，每行 16 B。
  一行包含四个连续的 25 bit 记录，映射该 CTU 的四个 16×16 横向网格。
- 每条记录：低 12 bit 为有符号 y，接下来 12 bit 为有符号 x，第 24 bit 为实验识别的
  inter 标记；128 bit 中未使用的高位不解析。符号按 12 bit 补码扩展。
- 行列超出实际图像的网格、I 帧内容、未使用的重建槽和分配尾部都可能包含旧数据。
  **不能将全部 24 KiB 直接遍历成有效向量**。

这套解释通过整幅运动、亚像素运动、左右区域、四象限和逐帧变向测试；
多参考帧、B 帧、其他分辨率和固件版本未验证。

## 耗时口径

640×400 P 帧从调用 SendFrame 前到 GetStream 返回，六组均值约 **2.59–2.68 ms/帧**。
这是不按墙钟 20 Hz 节流的文件输入实验，配置的编码帧率为 20；不是实时相机到向量的延迟测量。
计时不含输入文件读取及图像填充，也不含之后的诊断。

当前诊断会逐帧读取 proc、保存原始缓冲区、格式化并落盘 1000 行 CSV，额外均值约
**6.9–7.3 ms/帧**。这些是诊断操作，不能当作正式内存接口的解析开销；本次没有测量
去掉诊断后的最小向量获取耗时，也没有证明整条 VIO 流水线能加速。

## 复现

本机生成测试图并交叉编译：

```bash
cd /home/ncer/sophpi
/usr/bin/python3 -S scripts/vio-compare/probes/codec-mv/make_device_input.py
python3 scripts/vio-compare/probes/codec-mv/build_device.py
```

将 `install/venc-mv-device-20261017/` 的 `sample_venc_probe`、六个 `.yuv`，以及本目录
`run_device.sh` 复制到板上的 `/mnt/data/venc-mv-probe-20261017/`，然后在板上执行：

```sh
sh /mnt/data/venc-mv-probe-20261017/run_device.sh
```

该 SDK sample 会初始化全局 SYS/VB，因此运行前应停止其他多媒体程序。
本次开始时板上没有相机、录制或 VIO 应用在运行。

回传 `csv-*` 目录后，在本机执行：

```bash
/usr/bin/python3 -S scripts/vio-compare/probes/codec-mv/summarize_device.py
```

验证器将板端 CSV 与原始缓冲区的独立位解析比较，并逐帧检查已知运动。
原始码流、快照、CSV、日志和汇总：

- 板端：`/mnt/data/venc-mv-probe-20261017/csv-*/`
- 本机：`install/venc-mv-device-20261017/`
- 汇总：`install/venc-mv-device-20261017/device-results.json`

# H.264 是否能提供更多向量

后续板端直读实验见 [H264-BOARD.md](H264-BOARD.md)：已识别四组运动上下文值，完整逐分区表尚未打通。

## 实测结果

使用 SG2002 **硬件 H.264 编码**完整 UZH-FPV `indoor_forward_6`：1970 帧，640×480，
Normal-P、GOP 60、固定 I/P QP 20、30 fps 编码配置。与之前硬件 H.265 使用相同原始左图及参数。
两种编码的 QP 数值相同不代表相同码率或重建质量。
原始图像纳秒时间戳与板端 `ENCODED` 日志逐帧核对，未丢帧。

**本轮比较的是两种获取方式，并非两种编码标准的全部向量能力：**

- H.265：目前已验证可在板端直接读取的 **16×16 collocated MV 摘要表**。
- H.264：板上硬件生成码流，回传电脑，通过 FFmpeg 解码器导出**完整帧间分区向量**。
  电脑负责解析，不是电脑软件编码；板端没有运行 FFmpeg，也尚未实现 H.264 向量直接导出。

| 指标 | H.265 摘要表 | H.264 完整分区 |
|---|---:|---:|
| 总输入帧数 | 1970 | 1970 |
| 有向量的帧数 | 1937 | 1937 |
| 累计向量数 | 1,416,621 | 2,213,471 |
| 每个 P 帧平均向量数 | 731.3 | 1142.7 |
| 原图 LK 特征获得向量初值的比例 | 66.3% | 74.1% |
| 有初值的浅层尝试中，完整补跑的比例 | 4.6% | 1.7% |
| 所有输入匹配点中，执行完整 LK 的比例 | 36.7% | 27.1% |
| 位置 ATE RMSE，m | 0.2445 | 0.2423 |

向量条数增加约 **56.2%**，特征初值覆盖率增加约 **7.8 个百分点**。
分区变小会增加条数，但不按同样倍数增加空间覆盖率；有更多记录不意味着所有特征均有可靠初值。

H.264 实际分区统计：

| 分区大小 | 向量数 |
|---|---:|
| 16×16 | 1,048,135 |
| 8×16 | 417,056 |
| 16×8 | 475,036 |
| 8×8 | 273,244 |

本轮没有导出 4×4 分区，不能按标准允许的最小分区假定当前硬件一定使用它。
关于 H.264 可变分区的标准背景可参考 [Fraunhofer HHI 的分区说明](https://www.hhi.fraunhofer.de/en/departments/vca/research-groups/video-coding-technologies/research-topics/past-research-topics/tree-structured-partitioning-for-motion-compensated-prediction.html)。

## LK 与精度验证口径

沿用本机 FP64、单目 150 点、16×15 窗口、原有标定及噪声，使用原始灰度图进行 LK。
仅替换编码向量缓存，保持相同的浅层 LK、残差/初值偏差门槛与完整补跑策略。
H.265 对照复用上一轮同配置的本机轨迹；H.264 完整回放一次。
两组均完成 1970 帧、输出 1782 个初始化后有限状态。

特征统计排除首次初始化帧，覆盖 1781 次匹配调用；因向量不同，后续保留的特征集合会变化，
覆盖率是各自 VIO 前端中的实测比例，不是固定同一批特征逐点对照。
ATE 使用共同的 816 个真值时间戳、约 30.15 秒，SE(3) 对齐、不拟合尺度，
保留官方相机时间偏移。真值没有覆盖完整序列。
ATE 差别小，本轮只能说明没有观察到明显精度退化，不能据此宣称 H.264 提高了精度。

本轮没有部署 LK 到 A53 重测速度，没有测量 H.264 板端 MV 接口开销。
电脑解码导出只用于评估潜力，不能把缓存回放的 LK 节省当成实际板端净收益。

## 板端直接导出的现状

之前的 H.264 试编码没有发现 H.265 那样独立命名的 `mvCol` 分配。
公开的 `VENC_STREAM_S` 不直接给出逐块 MV。
SDK 内部 `vpuapi.h` 有 `EncReportInfo mvInfo` 及 `ENC_SET_REPORT_MVINFO` 的说明，
但尚未验证本板当前固件的实际支持、使能方式和缓冲区格式。
不能直接复用 H.265 的私有内存解析器读取 H.264。

下一步若继续，应先验证 H.264 的固件报告/驱动导出路径，再测板端获取延迟及 LK 总耗时。
本轮没有改内核、固件或默认 VIO 配置。

## 复现

板端在多媒体程序空闲时，复用已部署的文件输入探针与 FPV 图片：

```sh
probe=/mnt/data/openvins-codec-shallow
work=/mnt/data/venc-h264-compare-20261017
mkdir -p "$work"
cd "$work"
"$probe/cleanup_idle" --probe-idle
truncate -s "$((640 * 480 * 3 / 2 * 1970))" input-sparse.yuv
VENC_MV_FRAME_LIST="$probe/fpv/frames.txt" timeout 180 "$probe/sample_venc_probe" \
  -c 264 -w 640 -h 480 -i input-sparse.yuv -o hardware -n 1970 \
  --rcMode=4 --iqp=20 --pqp=20 --gop=60 --gopMode=0 \
  --srcFramerate=30 --framerate=30 --getstream-timeout=3000 --sendframe-timeout=3000 \
  > encode.log 2>&1
"$probe/cleanup_idle" --probe-idle
rm -f input-sparse.yuv
```

把 `hardware.h264` 和 `encode.log` 回传至 `install/openvins-codec-h264/`，在电脑执行：

```bash
python3 scripts/vio-compare/probes/codec-mv/h264_export.py \
  install/openvins-codec-h264/hardware.h264 \
  install/fisheye-benchmark/openvins/uzh-input/stereo.csv \
  install/openvins-codec-h264/fpv
```

导出程序会先检查全部 SPS/PPS/切片头：单参考帧、无参考列表重排、无长期参考，
33 个 I 帧、1937 个 P 帧；之后检查完整解码帧数及向量只引用过去帧。
这些检查配合 Normal-P 配置，保证缓存使用相邻输入帧的时间关系。
需要已存在 `install/openvins-codec-mv/extract_mvs`，构建方式见 `prepare.py`。

原图 VIO 回放使用上一轮 `openvins-codec-retry` 诊断程序：

```bash
OV_CODEC_IMU_AHEAD=.03 OV_CODEC_MV_MODE=rect OV_CODEC_MV_LK=shallow \
OV_CODEC_MV_RETRY=on \
OV_CODEC_MV_BIN="$PWD/install/openvins-codec-h264/fpv/vectors.bin" \
OV_CODEC_MV_DETAIL="$PWD/install/openvins-codec-h264/fpv-detail.csv" \
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
install/openvins-codec-retry/host/run_record.r1000 \
  install/openvins-codec-shallow/host-config-fpv/estimator_config.yaml \
  install/fisheye-benchmark/openvins/uzh-input \
  install/openvins-codec-h264/fpv-poses.csv 0 \
  > install/openvins-codec-h264/fpv-replay.log 2>&1
cp /tmp/codec-shallow-timing.csv install/openvins-codec-h264/fpv-timing.csv
/usr/bin/python3 -S scripts/vio-compare/probes/codec-mv/h264_summary.py
```

全部结果保存在 `install/openvins-codec-h264/`，包括码流、编码日志、参考帧检查、
逐块 MV、转换后缓存、VIO 轨迹和 `summary.json`。
板端原始图片没有改动；本轮临时代码流确认 SHA256 与电脑副本一致后清理，编码结束 ION 使用为 0。

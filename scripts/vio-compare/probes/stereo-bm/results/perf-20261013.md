# StereoBM hardware perf findings, 2026-10-13

Measured on TideSense SG2002 **A53 at 1 GHz**, using
`dataset-20261012-084638`. Both configurations process **885 pairs**, with the
first **20 pairs excluded** from analysis. No VIO, ROS, IVE or TPU runs.
The OpenCV 3.4.20 NEON implementation and matcher parameters are unchanged.

## Sampling method

- Hardware PMU events: `cycles:u`, `L1-dcache-load-misses:u`, 499 Hz per event.
- `--clockid mono`, with exact monotonic read/rectify/BM/depth frame boundaries.
- Percentages are weighted by sample periods; they are **self costs**.
- PGM reads, diagnostic writes, CSV writes and warmup are excluded from the
  compute rankings. No call graph is used or inferred.
- Traces and outputs are written to tmpfs, then copied to SD after each run.
- Exact matching unstripped ELF is retained. Neither trace has LOST events;
  host decoding has no warnings and unresolved compute period is negligible.

885 timestamp/coverage values match the original unprofiled run for each
configuration. Depth PNGs at frames 150, 400 and 600 are byte-identical.

## Where compute cycles go

Percentages in this table use **all compute stages** as the denominator:

| Stage/function | 320x200 / D32 | 640x400 / D64 |
|---|---:|---:|
| Entire BM stage | 74.60% | 88.08% |
| Entire rectification stage | 22.77% | 10.84% |
| Depth conversion stage | 2.63% | 1.09% |
| SIMD matching kernel self | 64.19% | 83.22% |
| Bilinear remap kernel self | 20.34% | 9.37% |

The stage rows and function rows overlap and must not be added together.

## Within BM

Denominator: cycles sampled inside the **BM stage** only.

| Function | 320x200 / D32 | 640x400 / D64 |
|---|---:|---:|
| `findStereoCorrespondenceBM_SIMD<short>` | **86.05%** | **94.49%** |
| `filterSpecklesImpl<short>` | 6.67% | 2.45% |
| `validateDisparity` | 4.76% | 1.88% |
| `prefilterXSobel` | 1.86% | 0.98% |

Thus the dominant BM work is the existing NEON matching kernel. Removing
postfilters would affect depth quality and addresses a much smaller portion
of the measured cost.

## Instruction regions in the SIMD kernel

Assembly was decoded with the GCC 11 AArch64 objdump and correlated with the
current OpenCV 3.4.20 source. The following regions are disjoint and their
denominator remains **all BM-stage cycles**, not just kernel cycles:

| Region | 320x200 / D32 | 640x400 / D64 |
|---|---:|---:|
| Sliding horizontal difference-buffer update plus texture accumulator | **34.82%** | **58.01%** |
| Vertical SAD update and vector minimum/index search loop | **19.36%** | **18.07%** |
| Uniqueness setup and vector checks | **16.21%** | **10.37%** |

The difference update reads right-image candidate bytes and the old byte
difference buffer, broadcasts the reference pixel, computes `uabd`, widens
bytes, updates 16-bit sums, and writes the new difference buffer and sums.
Representative sampled instructions are:

```asm
408b34  ldrb   w8, [x28, x23]
408b38  dup    v4.16b, w8
408b48  ldr    q0, [x1, x0]
408b4c  ldr    q1, [x2, x0]
408b50  uabd   v0.16b, v4.16b, v0.16b
408b60  str    q0, [x3, x0]
408b70  ldp    q2, q1, [x5]
408b74  uqadd  v0.8h, v1.8h, v0.8h
408b7c  sqsub  v0.8h, v0.8h, v3.8h
408b84  stp    q1, q0, [x5]
```

The difference-update/texture region accounts for **65.06% / 74.21% of
BM-stage L1 refill periods** at 320x200 / 640x400. The SAD/minimum vector loop
accounts for another **22.46% / 18.68%**. Uniqueness checks account for less
than 1% of refill periods.

These events localize memory traffic around difference-buffer and sum-buffer
updates. They do **not** establish the fraction of time stalled on DRAM, the
L2 miss rate, or the benefit of any proposed tiling change. PMU interrupts are
not precise instruction tracing: samples attributed to `dup`/`uabd` can reflect
preceding loads. Optimization priority should target these loops and their
data access, then measure whether a change improves performance.

The uniqueness loop visibly expands 16-bit costs to 32-bit vectors and uses
`cmgt`, `sxtl`, `umaxv`, `fmov`. It is a real secondary hotspot at 320x200, but
it is smaller than the two matching/accumulation regions combined.

## Timing during profiling

| Configuration | Rectify | BM | Depth | Compute total |
|---|---:|---:|---:|---:|
| 320x200 / D32 | 8.38 ms | 27.16 ms | 0.95 ms | 36.49 ms |
| 640x400 / D64 | 28.52 ms | 231.04 ms | 2.82 ms | 262.38 ms |

Hardware sampling adds overhead. These numbers are approximately 1.7% and
4.6% above the prior unprofiled compute totals; use the earlier **35.88 ms /
250.84 ms** numbers when quoting baseline processing speed. PGM reads remain
about 55 ms/pair and are excluded from the hotspot tables.

## Artifacts and reproduction

- `RUN-INFO.json`: binary/source hashes, exact code-region ranges and results.
- `*-perf.data`: raw hardware traces.
- `*-samples.txt`, `*-summary.json`: decoded samples and per-stage rankings.
- `*-intervals.csv`, `*-timing.csv`: phase windows and wall-clock timing.
- `*-annotate.txt`: full matching-kernel instruction annotations for both events.
- `*-events.txt`: event counts and record-loss audit.
- `stereo_bm.sym`, `symfs/`: exact symbols and board-path mapping.
- `board-profile.log`: clock, temperature and successful run completion.

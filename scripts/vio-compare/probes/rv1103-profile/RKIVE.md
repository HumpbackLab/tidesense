# RV1103 RKIVE 金字塔和 LK 加速试验（2026-10-25）

**联合替换已在设备完成 400 帧原生初始化回放：前端 66.49 → 24.93 ms，
纯 VIO 148.19 → 104.75 ms，延迟降低 29.3%。**
计入图像文件读取解码为 126.83 ms/帧，离线吞吐约 7.88 fps。
ATE RMSE 为 5.10 cm，原软件基线 4.63 cm；本段轨迹没有明显发散。

这是独立的实验后端。硬件的金字塔层数、迭代上限、定点坐标和终止阈值与原
OpenCV 实现不同，不能把它称为逐位等价替换；已经补充纯 CPU 参数对照和真值评分。

## 配置及对照

设备仍为 `172.32.0.93` 的 RV1103/Cortex-A7，固定 1.104 GHz，使用已经启动的
perf 诊断镜像。直接加载镜像中已匹配重编的 `/oem/usr/ko/rve.ko`，驱动版本
1.0.6，硬件版本显示 `[2021]58.1a`。本轮未重新烧写内核或固件。

输入、200 特征、11 clones、FP64 后端、原生初始化、FEJ、在线标定、RANSAC、
MSCKF χ² 门控和 5 帧预热均沿用 [软件基线](RESULTS.md)。
每个完整测试总处理 495 帧，统计初始化和预热之后的 400 帧，轨迹覆盖 20.2 秒。

| 模式 | 金字塔/导数 ms | LK ms | 前端 ms | 后端 ms | 纯 VIO ms | ATE RMSE cm |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原软件基线，两轮合并 | 15.58 | 33.68 | 66.49 | 80.63 | 148.19 | 4.63 |
| 软件 4 层/20 次对照 | 15.04 | 29.15 | 61.74 | 81.03 | 143.83 | 5.52 |
| RKIVE 金字塔 + 软件 LK | 15.08 | 29.10 | 62.44 | 80.82 | 144.32 | 5.44 |
| 软件金字塔 + RKIVE LK | 6.12 | 6.13 | 29.16 | 79.60 | 109.80 | 5.16 |
| **RKIVE 金字塔 + RKIVE LK** | **3.38** | **3.67** | **24.93** | **78.71** | **104.75** | **5.10** |

表中耗时为无 perf 的均值，含 CPU↔CMA 拷贝、缓存同步、提交及等待完成。
软件金字塔 + 硬件 LK 无需 CPU Scharr 导数；仅金字塔模式则必须补齐 OpenCV
要求的图像边界和 Scharr 导数，其开销计入金字塔阶段，因此单独替换没有明显收益。

硬件联合模式相对软件 4 层/20 次对照，纯 VIO 延迟仍降低 **27.2%**，
表明主要收益并非只来自减少层数和迭代次数。由于其余数值差异仍然存在，
这不是严格相同数值算法的硬件/软件加速比。

原配置请求 OpenCV maxLevel=5、最多 30 次迭代、15×15 窗口；752×480 下
实际可构建到 level 4，共五层。RKIVE API 允许 maxLevel≤3（四层）、
迭代数≤20、每批≤500 点。适配器保留全部特征，超过 500 点时分批，不通过丢点降载。
硬件 API 不暴露窗口参数，适配器仅接收原有的软件 15×15 配置；硬件内部窗口的
精确尺寸尚未从手册确认，也不能宣称其与 OpenCV 完全相同。

硬件输入/输出点使用 S25Q7，即 1/128 像素。当前参数为 `minEig_q8=1`、
`eps_q11=1`、使用初始预测位置；OpenCV 对照仍采用自身的 epsilon=0.01 和
minEigThreshold=0.0001。SDK 的归一化定义与 OpenCV 不完全一致，不能宣称这两个
阈值精确等价，也没有放宽后端的 χ² 或 RANSAC 门限。

后端约 78.7 ms，占纯 VIO 时间约 75%。完成前端卸载后，主要瓶颈已经转向后端。

## 硬件路径及内存

- 使用 SDK 静态 `librve.a`，调用 `RK_MPI_IVE_Pyramid_Create` 与
  `RK_MPI_IVE_LKOpticalFlowPyr`，阻塞查询确认完成，错误会退出，不自动回退软件。
- 两个帧缓冲交替保留上一帧和当前帧金字塔；联合模式直接复用 DMA 金字塔，
  避免每次 LK 重新上传。仅 LK 模式的双帧上传成本已计入计时。
- SDK 默认分配器依赖 DRM/MPI，诊断镜像未启动那些厂商服务。本适配器通过
  RK CMA heap 分配 DMA-buf，并用 DMA_BUF_IOCTL_SYNC 处理 CPU/硬件缓存同步。
- 此 SDK 的 RK heap 没有 GET_PHYS ioctl，inactive-CMA 映射也不能从 pagemap
  取得 PFN；实验适配器读取 `/proc/rk_dma_heap/dma_heap_info`，按已持有 DMA-buf
  的 inode 查找并验证物理范围和大小。该方法依赖当前 SDK 的 procfs 格式及 root
  权限，不是通用稳定的内存分配 API。
- 两帧 DMA 图像、临时区、点和 SDK 描述符池的分配布局约 2.34 MiB，来自已预留
  的 24 MiB CMA。联合模式进程峰值 RSS 为 8324 KiB；RSS 不包含这些特殊映射，
  不能仅凭 RSS 宣称总物理内存占用。每次退出后 DMA heap 总占用恢复为 0。

合成一像素平移探针取得 200/200 个有效点，平均 dx=0.9975、dy=0.0311 像素；
金字塔约 2.7 ms、LK 约 3.6 ms，硬件中断计数确实增长。该探针只是基本连通性
检查，最终精度结论采用完整 EuRoC 回放的真值评分。

## perf 与一致性

联合模式另跑一轮 `cycles:u`、99 Hz 采样，得到 4363 个样本，其中 4076 个
落在初始化和预热后的 VIO 处理区间。LOST、THROTTLE、UNTHROTTLE 记录均为 0。

| 用户态自身 cycles 热点 | 占比 |
| --- | ---: |
| Eigen FP64 矩阵乘法主内核 | 29.32% |
| MSCKF 测量压缩 | 24.31% |
| 提取边缘协方差 | 3.88% |
| Eigen FP64 左矩阵打包 | 2.44% |

采样中 CPU `LKTrackerInvoker` 样本为 0。采样轮完成 495 次硬件金字塔和
494 次硬件 LK 调用，末态 RVE 中断总计数为 12661（包含全部模式试验和探针）。
硬件等待的耗时体现在墙钟计时中，不会作为 CPU 用户态 cycles 样本计入热点分母。

采样轮纯 VIO 为 106.111 ms，主表使用无 perf 的 104.747 ms。
两轮联合模式的轨迹逐字节一致，SHA256 为
`a40791b26bee2391e26295054488d88ccc727ff8ea189eadec2a2380f574d442`。
新可执行文件的原软件路径也做了 100 帧 smoke，其 10 个初始化后状态与原基线
对应前缀逐字节一致。

## 构建和运行

```sh
python3 scripts/vio-compare/probes/rv1103-profile/build-rkive.py
```

脚本读取已有 FP64 基线构建的编译参数和链接命令，只重编 TrackKLT 和新增
适配器，复用其他已验证的后端对象。未改写原基线源码或可执行文件。
源码为 [rkive-frontend.cpp](rkive-frontend.cpp)、
[rkive-memory.c](rkive-memory.c) 和 [rkive-probe.c](rkive-probe.c)。

设备已部署 `/root/rkive-test-20261025/bin/openvins_mono`，共用已有数据与配置。
复跑联合模式：

```sh
sh /root/rkive-test-20261025/run-rkive-board.sh both both-recheck
```

脚本按需加载镜像中匹配的 RVE 驱动，设置 performance，结束后恢复调用前的频率
策略。其他模式名为 `software`、`software4`、`pyramid`、`lk`。
本轮全部试验结束后已恢复 `ondemand`；RVE 模块保留加载，pd_ref=0，无回放进程残留。

板端日志：`/root/rkive-test-20261025/results/`。
本机产物：`install/rv1103-rkive-20261025/`，包含构建命令、ELF、raw perf、
逐帧计时、轨迹及 ATE。完整汇总为 [rkive-results-20261025.json](rkive-results-20261025.json)。
